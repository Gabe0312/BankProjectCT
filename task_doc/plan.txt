4. DATABASE DESIGN
-------------------------------------------------------
4.1 MongoDB Collections

MongoDB stores data as JSON-like documents instead of tables.
Transactions are embedded inside the account document.
No foreign keys needed - relationships handled via embedded documents.

USERS COLLECTION
{
  "_id":          ObjectId (auto-generated),
  "name":         String,
  "email":        String (unique),
  "created_at":   DateTime
}

ACCOUNTS COLLECTION
{
  "_id":          ObjectId (auto-generated),
  "user_id":      ObjectId (reference to users._id),
  "balance":      Decimal,
  "account_type": String (SAVINGS / CHECKING),
  "created_at":   DateTime,
  "transactions": [
    {
      "txn_id":     ObjectId,
      "txn_type":   String (DEPOSIT / WITHDRAWAL),
      "amount":     Decimal,
      "created_at": DateTime
    }
  ]
}

6. BUSINESS RULES
-------------------------------------------------------
  - Cannot withdraw more than balance
  - Deposit amount must be positive
  - Maintain transaction record for each deposit/withdraw

-------------------------------------------------------
6.1 CRUD MAPPING
-------------------------------------------------------
  CREATE  → POST   /api/accounts                      (create account)
  READ    → GET    /api/accounts/{id}                 (get account details)
  READ    → GET    /api/accounts/{id}/transactions    (get transaction history)
  UPDATE  → POST   /api/accounts/{id}/deposit         (update balance)
  UPDATE  → POST   /api/accounts/{id}/withdraw        (update balance)
  DELETE  → N/A    (intentionally excluded - banks never delete records)

KEY DESIGN DECISIONS
-------------------------------------------------------
1. FastAPI over Flask
   → Auto-generates Swagger UI at /docs with zero config
   → Built-in Pydantic validation protects banking logic

2. MongoDB Atlas over MySQL
   → Document model fits JSON API responses naturally
   → Transactions embedded in account document = fewer queries
   → Cloud hosted = no local DB setup needed
   → Motor async driver pairs perfectly with FastAPI async

3. In-memory store for today
   → Python dictionaries used as temporary data store
   → No DB setup needed, focus is on API structure
   → Easily swapped out for Motor + MongoDB Atlas later

4. Separate controllers, services, repositories
   → Follows MVC pattern, clean separation of concerns, easy to scale

5. React JSX for frontend
   → Component reusability across all pages
   → Bootstrap first for speed, transition to Tailwind for customization
   → Axios in api.js as single point of contact to FastAPI

6. Bootstrap → Tailwind transition plan
   → Start with Bootstrap for fast UI development
   → Swap to Tailwind class names per component when ready
   → No restructuring needed, only class name changes

4. Account numbers auto-generated
   → Random unique 10-digit number on account creation

5. Balance never goes negative
   → Enforced at the route level before any DB write

6. All transactions logged
   → Every deposit/withdrawal creates a transaction record, never deleted
